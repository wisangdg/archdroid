## Findings

### F1 — `waydroid app remove` reports success while the package remains

- Observed on Waydroid `1.6.3-1` with the stock Arch Rust binder driver.
- `waydroid app remove org.fdroid.fdroid` → exit `0`, log
  `Failed with code: -3` / `Failed to uninstall package`.
- `waydroid app list` and `pm list packages` still show the package.
- `sudo waydroid shell cmd package uninstall org.fdroid.fdroid` → `Success`,
  package gone.
- ArchDroid `waydroid_uninstall_app` only mapped the process exit code, so the
  UI would show a successful uninstall that did not happen.
- **Fixed:** `waydroid_uninstall_app` now uses `adb uninstall` when adb is
  available (authoritative, live-tested: `Success` and the package disappears).
  Without adb it verifies `waydroid app list` after `app remove` and returns an
  actionable error if the package is still present. Regression coverage:
  `app_list_output_is_parsed_into_package_names` and adb argv tests.

### F2 — Invalid APK install is reported as success

- `waydroid app install ~/test-data/invalid.apk` → exit `0`, no output, no
  package added.
- `waydroid app install` returns after the binder/platform request; the
  Android-side failure is not reflected in the exit code.
- ArchDroid `waydroid_install_apk` only mapped the exit code, so an invalid APK
  would appear installed.
- **Fixed:** installs validate the APK container first (ZIP magic +
  `AndroidManifest.xml`) and use `adb install -r` when adb is available, which
  returns the real package-manager result (live: invalid APK exit 1 with
  `INSTALL_PARSE_FAILED_NOT_APK`). Without adb, the structural check still
  rejects text/manifestless files before the CLI can return a false success.
  Regression coverage: `apk_check_rejects_text_and_manifestless_zips` and adb
  argv tests.

### F3 — Preflight error left the streaming terminal stuck

- Phantom install (and any streaming command rejected before `cmd-started`)
  opened the terminal modal and left it on “Awaiting elevated process stream…”
  with no error, because `runStreamingTask` ignored non-`busy` error results.
- **Fixed:** a `taskStartedRef` distinguishes pre-start errors from a task that
  actually streamed; the terminal is closed and the backend message is shown as
  “Operation Failed”. Live re-test shows the Phantom preflight message above.
- **Related:** `run_phantom` ignored its `CommandResult` and always toasted
  “Keymapper Launched”; it now checks `status` and renders the error. Live
  terminal-missing test passed.

### F4 — Package preview was never wired into the confirmation modal

- The handlers stored `packagePreview` in state, but `<ConfirmModal>` did not
  receive it, so the P0-7.3 package list/command was invisible.
- **Fixed:** pass `packagePreview={confirmModal.packagePreview}` and added a
  regression assertion. Live GApps modal now shows “No system packages will be
  installed” when nothing is missing.

### F5 — App list stayed stale after install/uninstall

- `adb uninstall` succeeded and `pm list packages` was empty, but the card and
  counter remained until the app was restarted, because Waydroid removes the
  `.desktop` entry asynchronously after `get_waydroid_apps()` had reloaded. The
  same lag appeared after a fallback install without adb.
- **Fixed:** a second `loadApps()` 1 s after the immediate reload, for both
  install and uninstall. Live uninstall re-test showed “App Removed”, 11 apps,
  and the card gone without a restart; the install fallback reached 12 apps once
  reloaded.

### F6 — Cancel troubleshooting text is misleading (fixed)

- Cancelling a root task previously showed `EXECUTION FAILED` plus “Root authentication may have been rejected…” even though the log says `cancelled` and the process was intentionally stopped by `cancel_task`.
- **Fixed:** `detectStepProgress` in `stepConfigs.js` now detects `[CANCELLED]` / cancellation state, and `TerminalModal.jsx` sets the phase header to “Operation Cancelled” and displays cancellation advice. (The original wording, “No modifications were completed”, was wrong once a stage had finished; since 0.1.2 it says completed stages stay applied and the interrupted one may be incomplete.)

### F7 — Elevated timeout/cancel could not kill the root process group

- Live timeout test: the app (uid 1000) called `kill` on the elevated process
  group, which was root-owned; `kill -TERM -- -PGID` returned
  `Operation not permitted`. The root `sudo`/`bash`/`sleep` tree survived the
  120 s deadline, the terminal never resolved, and no `timeout` code was
  emitted. This invalidated the previous unit-only assumption for P0-4.1/4.2.
- **Fixed:** the generated root script now starts a watcher that polls a
  user-owned cancel file (`/tmp/archdroid-cancel-<pid>-<task>`). On timeout or
  Cancel the app creates that file; the root watcher runs `kill -TERM 0` from
  inside the root group. The script's EXIT trap also kills the watcher and
  removes the private workdir.
- **Verified live:** timeout now logs “did not finish within 120s and was
  terminated”, leaves no root processes and no marker; Cancel logs
  “sudo was cancelled” and leaves no root processes.
- Unit tests updated for the new trap/watcher and `wait_with_deadline` signature.

### F8 — Phantom launch uses the client without a daemon (fixed)

- Phantom install passes: `phantom-gui 1.1.0` builds, `phantom-server.jar` is
  built with `d8`/`android.jar`, and `~/.local/bin/phantom` plus `phantom-gui`
  are installed.
- `run_phantom` previously spawned a terminal running bare `phantom`. That binary is the
  client and exits with `ERROR IPC error: cannot connect to daemon`; upstream
  expects `phantom-gui` desktop app.
- **Fixed:** `run_phantom()` in `src-tauri/src/lib.rs` now checks for `phantom-gui`
  (in PATH, trusted dirs, or `~/.local/bin/phantom-gui`) and launches it directly
  as a native Wayland GUI application without an unnecessary terminal wrapper.
  If only the CLI is present, it falls back to the terminal; if neither is
  installed, it returns an explicit typed `not_found` error directing the user
  to click "Install / Update Phantom" first.

### F9 — Cancelled root tasks leaked their work directory (fixed in 0.1.1)

The installer bodies start with `set -eu`, which also applies inside traps.
The cancel watcher ends with `kill -TERM 0`, killing itself too, so the trap's
`kill "$ARCHDROID_CANCEL_WATCH"` failed and bash exited before `rm -rf`. The
TERM trap also did not exit, so a script could resume its next root command.
Reproduced outside the app with a minimal `sudo bash -c` script; the existing
cleanup tests used a hand-written trap and missed it. Fix: cleanup in an EXIT
handler that tolerates a dead watcher, and `exit 143` on HUP/INT/TERM; the new
test `cancel_file_ends_a_set_e_script_and_removes_its_work_dir` runs the real
prelude and fails on the old trap.

Cosmetic: after a cancel the stepper showed stage 1 spinning, and the wipe
dialog kept the title "Factory Reset in Progress..." once finished; both fixed
on `main` after 0.1.1 and verified live below. The Start tooltip can stay
visible when the Stop button replaces it under a cursor that does not move;
each button's `title` is correct and the tooltip refreshes on the next mouse
move. Not fixed.

### F10 — Install from a frozen container never reached the app list (fixed)

`with_device` resumed a frozen container for `adb install`, then froze it again
40 ms after adb returned. Waydroid writes `waydroid.<pkg>.desktop` (the app
list's source) only after Android reports the package change, so the freeze
stopped that write: the install succeeded but the card stayed missing until
something else resumed the container. Uninstall had the same race. Fix:
`install_apk`/`uninstall_app` wait (≤ 10 s, cancellable) until the set of
launcher entries changes before the container is frozen again; in the VM the
change landed within the same second.

### F11 — "Keymapper Launched" for a GUI that died at once (fixed)

`run_phantom` treated a successful `spawn()` as a successful launch and never
reaped the child. `watch_launch` now gives the process 1.5 s: an early
non-zero exit becomes an error with the exit status; a running process is
reaped on a background thread.
